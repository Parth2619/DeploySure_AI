# Build DeploySure on stdlib, LangGraph and rules

DeploySure's planned design is sound and can be built almost entirely from the standard library plus three packages: `langgraph`, `pytest` and the plain `ollama` client. LangGraph 1.2.15 (released 2026-10-12) installs and runs on Python 3.14.5 even though PyPI lists no 3.14 classifier, and a bounded Critic-retry loop with `retry_count`, a `replan` node and a `manual_review` exit was run end to end and works ([PyPI](https://pypi.org/pypi/langgraph/json)). pytest 9.1.1 officially supports 3.14, and a `--junitxml` runner, an `ast`-based function diff and an import-graph BFS were all run locally on Windows 11 and behaved as needed ([pytest changelog](https://docs.pytest.org/en/stable/changelog.html)). No mature open-source "multi-agent release gate with a Critic" exists, so DeploySure's combination of a deterministic rule floor, a Critic that forces a bounded reassessment and replayable scenarios is a defensible niche; the nearest prior art is the hackathon project DeployGuard, which should be cited honestly as related work. The biggest open risks are not in the code but in the live demo: a 7B model on a CPU laptop may take 2 to 3 minutes per run, structured-output reliability of small models is unmeasured, and a few CLAUDE.md details (the `langchain-ollama` option, Windows timeout handling, the `trace` reducer) need small corrections before coding starts.

## LangGraph 1.2.15 fits the design with four pitfalls to avoid

The API shape in CLAUDE.md is current: `StateGraph(TypedDict)`, `add_node`, `add_edge(START, ...)`, `add_conditional_edges(src, fn, path_map)` and `compile()` ([Graph API docs](https://docs.langchain.com/oss/python/langgraph/graph-api)). A routing function returning `"end" | "replan" | "manual_review"` with an explicit path map ran correctly, and because `route_after_critic` is a pure function of state it can be unit tested with plain dicts for the three required cases. A test run with an always-rejecting Critic produced exactly three passes (MAX_RETRIES = 2), two `replan` steps, then `manual_review`, which confirms the cap logic. The official evaluator-optimizer example has no iteration cap at all, so the `retry_count` guard is the project's own contribution and the right mitigation ([Workflows and agents docs](https://docs.langchain.com/oss/python/langgraph/workflows-agents)). Pass `config={"recursion_limit": 60}` as a backstop: exceeding it raises `GraphRecursionError`, and the docs (default 1000) disagree with the installed source (10007), so setting it explicitly sidesteps the mismatch.

Four pitfalls matter. First, keys without a reducer are overwritten, so `trace` must be `Annotated[list[str], operator.add]` and every node must return only its new line, never the old list plus a new line, or entries duplicate ([Graph API docs](https://docs.langchain.com/oss/python/langgraph/graph-api)). Second, `retry_count` must have no reducer because `replan` sets it to `n+1`. Third, a node returning a key missing from the TypedDict is silently dropped with no error (verified), so a typo in a state key fails quietly; unit tests that assert on final state keys catch this. Fourth, the same node names repeat across retries, so the UI must tolerate a second `planner` event. A node named `decision` with a state key `decision` compiled fine in 1.2.15, though older versions rejected it; rename one for readability.

For `stream_release_validation`, `graph.stream(inputs, stream_mode="updates")` yields one `{node_name: partial_update}` dict per finished node, which maps directly onto the contract's `{"node", "status", "state_update", "timestamp"}` event (verified). The update contains only what the node returned, not full state, so the generator should merge updates itself (append `trace`, overwrite the rest) to build `final_report` for the closing `node: "final"` event. A `version="v2"` chunk format wraps each chunk as `{"type","ns","data"}` and requires LangGraph 1.1 or later; the default shape is simpler and was verified ([Streaming docs](https://docs.langchain.com/oss/python/langgraph/streaming)). Scenario B's seeded wrong answer should key off `retry_count == 0` inside the decision node, which gives the sequence DEPLOY, Critic FAIL, replan, BLOCK, Critic PASS with `retry_count` 1.

## Similar projects validate the rules-first Critic and supply borrowable ideas

Nothing found matches DeploySure end to end, and no GitHub star counts could be retrieved except one, so none should be quoted. The closest are release-gate, a PyPI CLI that issues PROMOTE, HOLD or BLOCK verdicts with the evidence shown beside them ([PyPI](https://pypi.org/project/release-gate/0.9.3/)); DeployGuard, a June 2026 hackathon entry with five agents where a RiskAgent challenges the SecurityAgent, critical decisions come from deterministic code, and it fails closed to manual review ([lablab.ai](https://lablab.ai/ai-hackathons/band-of-agents-hackathon/impactonious/deployguard-multi-agent-pr-security-gate)); and TDAD (17 stars, MIT), which parses Python with `ast` into a graph to rank impacted tests, the same technique planned for `dependency_analyzer.py` ([GitHub](https://github.com/pepealonso95/TDAD), [arXiv 2603.17973](https://arxiv.org/pdf/2603.17973)). The Agentic Pull Request Reviewer is a LangGraph propose-then-verify design, structurally the same as Decision then Critic ([PyPI](https://pypi.org/project/agentic-pr-reviewer/0.2.0/)). The honest framing for the viva is that DeployGuard is the nearest prior art, and that "static analysis only" is also TDAD's stated limit, so DeploySure's limitation is normal rather than a weakness.

The academic case for the Critic design is strong. Huang et al. (ICLR 2024) show that LLMs cannot reliably self-correct reasoning without external feedback and can get worse, while self-correction works when grounded in a code executor ([arXiv 2310.01798](https://arxiv.org/html/2310.01798v1)). Judge models also show self-preference bias ([Wataoka et al.](https://arxiv.org/pdf/2410.21819)). Anthropic's agent guidance recommends programmatic gates and a maximum iteration count in evaluator-optimizer loops ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)). Together these justify the rule that the Critic checks the decision against the BLOCK/HOLD/DEPLOY table in code first, feeds the LLM real pytest results as external evidence, and lets the LLM write only the explanation. A Critic running the same model as Decision would tend to agree with it, which is why the verdict must never depend on the LLM agreeing; say this in the demo.

On risk factors, the literature supports the inputs of the planned formula without supplying weights. Change size and diffusion predict defects at commit level ([Kamei et al.](https://posl.ait.kyushu-u.ac.jp/~kamei/publications/Kamei_EMSE2015.pdf)), relative churn beats absolute churn ([Nagappan and Ball](https://microsoft.com/en-us/research/?p=151819)), and Google found failing tests tend to sit close to the changed code ([Google Research](https://research.google/pubs/taming-google-scale-continuous-testing/)). Meta's predictive test selection uses a gradient-boosted tree chosen for explainability but needs months of history ([Meta](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/)), which synthetic data cannot provide, so a rule-based dependency approach is the right choice. The 0 to 100 formula itself is custom: no published numeric weights were found, so describe it as "informed by" the literature, never "validated by" it. Two cheap ideas to copy: Harness runs everything when unsure about test selection ([Harness](https://harness.io/blog/continuous-integration/test-intelligence)), and release-gate shows evidence next to the verdict, which suggests a per-component risk breakdown and a "rules fired" list in `critic_result`.

## Ollama: use the plain client, a 3B default and a warm model

Use the plain `ollama` package (0.6.3, 29 Sep 2026) rather than `langchain-ollama` (1.1.0), because LangGraph does not need it and it pulls in the langchain-core stack ([PyPI ollama](https://pypi.org/project/ollama/), [PyPI langchain-ollama](https://pypi.org/project/langchain-ollama/)). Structured output is requested by passing a pydantic `model_json_schema()` as `format` with `temperature` 0, then validated with `model_validate_json`; the docs also advise echoing the schema in the prompt ([Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs)). Use `Literal["DEPLOY","HOLD","BLOCK"]` so wrong enum values fail validation, retry once, then fall back to the deterministic default and log it in the trace. The snippet in the notes was assembled from docs and not executed, so treat it as a starting point.

Model choice depends on Manc's hardware, which is unknown. qwen2.5 comes as 3b (1.9 GB) and 7b (4.7 GB) ([Ollama qwen2.5](https://ollama.com/library/qwen2.5)); llama3.2 3b is 2.0 GB ([Ollama llama3.2](https://ollama.com/library/llama3.2)). The one concrete CPU-only measurement found is 6.9 tok/s for a 3.8B model ([It's FOSS](https://itsfoss.com/testing-local-llms-without-gpu)), and other speed claims conflict. Estimating from those rates, a 150-token JSON answer takes roughly 20 to 30 s at 7B CPU speeds and 8 to 15 s at 3B speeds, so Scenario B with 5 to 6 LLM calls could take 2 to 3 minutes on a 7B model but about 1 to 1.5 minutes on a 3B model. That is an inference, not a measurement. Recommend `qwen2.5:3b` as the default, `qwen2.5:7b` only on a 16 GB machine after timing it, and avoid thinking models such as qwen3 unless `think=False` is used ([Ollama thinking docs](https://docs.ollama.com/capabilities/thinking)). The default keep-alive is 5 minutes, after which the model unloads ([Ollama FAQ](https://docs.ollama.com/faq)), so send a warm-up call before the demo with `keep_alive="30m"` and set a client timeout so a stuck model cannot hang the slot. Reproducibility with temperature 0 and a fixed seed is only "mostly" true on one machine and can drift across versions or quantisations ([SSD Nodes](https://www.ssdnodes.com/learn/ollama-temperature-and-sampling)); the deterministic floor and MockLLM, not the model, guarantee the demo.

## pytest and AST tooling: junitxml, importlib mode and function-level hashing

Parse results from `--junitxml` with `xml.etree.ElementTree` rather than scraping the summary line; it needs no dependency and gives per-test status ([pytest output docs](https://docs.pytest.org/en/stable/how-to/output.html)). Verified locally: v2.0 returned exit code 0, v2.2 returned code 1 with `test_refund` failed, and a nonexistent node id returned code 4 with no XML, so codes 4 and 5 must be treated as "selection error", never as a pass ([exit codes](https://docs.pytest.org/en/stable/reference/exit-codes.html)). Run `sys.executable -m pytest` with `cwd` set to each release folder and a per-release `pytest.ini` containing `--strict-markers -p no:cacheprovider --import-mode=importlib` and `pythonpath = .`; this let identically named modules in v2.0 and v2.2 run without collision. The junit `file` attribute is absent by default, so key tests on `classname` plus `name`.

Critical tests should use a registered `@pytest.mark.critical` marker. A `conftest.py` hook that appends `("critical", True/False)` to `item.user_properties` writes a `<property>` into the XML, giving status and criticality from one run (verified locally), though it requires the conftest inside every demo release folder. The alternative is a single `--collect-only -q -m critical` call and a set lookup, which needs no conftest. For the AST diff, comparing `ast.dump` per function ignores comments, whitespace and line numbers, flagged only real changes in a local test, and should strip docstrings first; key functions as `Class.method` and compare non-function top-level statements too, because a module constant such as a fee rate is not a function. Keep `difflib` for the human-readable diff only. The import graph is `ast.Import` and `ast.ImportFrom` filtered to local module names, inverted, then a BFS with a `seen` set (cycle safe); verified on a checkout, orders, payment example. Use flat modules and absolute imports in the demo shop so relative imports (`from .payment import x`, not handled by the snippet) never arise.

Windows adds three traps. The default text encoding here was cp1252, so pass `encoding="utf-8", errors="replace"` to subprocess and `read_text`. `subprocess.run(timeout=)` kills only the direct child, and on Windows `kill()` does not reach grandchildren; `taskkill /F /T /PID` fixed this in a local test ([subprocess docs](https://docs.python.org/3/library/subprocess.html)). For plain tests the `run` timeout is probably enough, but a Popen plus taskkill version is the safe upgrade. Use lists, never `shell=True`, because the project path "DeploySure AI" contains a space.

The main risks, in order of likely damage: live-demo latency on CPU (mitigate with the 3B model, short schemas, warm-up and the mock fallback plus recorded video); weak-model JSON failures (mitigate with `Literal` validation, one retry, deterministic fallback, logged in the trace, and measure over 10 runs per scenario as PLAN.md already says); silent state-key typos and duplicated trace lines (mitigate with end-to-end assertions on final state); a timeout leaving orphaned pytest processes on Windows (mitigate with taskkill); the grader or examiner asking about the seeded wrong decision (mitigate by disclosing it openly, as CLAUDE.md requires); and prior-art exposure if DeployGuard is not cited.

## Conclusion

The research changes the plan in small, practical ways rather than large ones. The architecture needs no redesign, but a few specific choices should be locked now: plain `ollama` over `langchain-ollama`, a 3B default model until timing proves a 7B model fits the 60-second target, junitxml parsing with exit-code checks, and a taskkill-capable timeout on Windows. The less obvious insight is that the Critic's value is explained by the self-correction literature: an LLM verifying itself without external evidence is unreliable, so DeploySure's rules-first, test-grounded Critic is a principled design, not just a demo convenience.

Going forward, the weakest area is empirical, not architectural. Nothing in the research measures how often a small local model returns valid JSON, or how long a full run takes on Manc's machine. Those two numbers, collected in Phase 4, decide whether the live demo runs on Ollama or on mock mode, and the project should be ready to present either way.
